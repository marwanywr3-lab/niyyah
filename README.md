## Run

Node 22+: `npm ci`, `node scripts/build.mjs`. Serve `public/` locally. Deploy Pages via the included Actions workflow after choosing GitHub Actions as the Pages source.

Arabic responsive PWA; offline shell and optional Quran package; Adhan prayer calculation with method and Asr selection; city coordinates; true-north qibla bearing; Umm al-Qura date and personal adjustment; local optional prayer records, personal duas, verse reflections and bookmarks; JSON export/restore; username/password auth API with salted PBKDF2-SHA256 (100,000 iterations), random hashed session tokens, 24-hour sessions, throttling and single-use recovery codes; optional client-encrypted AES-GCM snapshot vault with conditional version writes. ## Sana v0.2 operations

Use the existing single GEMINI_API_KEY Worker secret. Set SANA_DISABLED=true to stop provider requests. Authentication and explicit per-question consent are required. Only the current question (240 characters maximum) is sent to Gemini 3.5 Flash-Lite; history and personal records are excluded. Before generation, countTokens measures the complete generateContentRequest including instructions and schema. Reject when input count plus the 64-token generation cap exceeds 500. MINIMAL thinking and maxOutputTokens apply to the generation; usageMetadata.totalTokenCount is checked after it. There are no automatic generation retries and no second-key fallback. The D1 reservation remains 500 on an ambiguous failure, preventing an accidental free retry. Each account retains its 10,000-token monthly anniversary allowance, 10-second spacing, one in-flight request and idempotent request IDs. The existing conservative global application budget remains $1 (5 USD-micros per token); it is not a Google billing report. Replies retrieve stored sources rather than generating religious content, and long texts link to the source instead of truncating scripture. The header opens Sana on every page; Quran verse-number buttons and study actions open a contextual panel. Tafsir is linked to the exact verse at QuranEnc (Al-Muyassar); the publisher text is not republished or paraphrased because version metadata is unavailable from its Arabic API catalog. Opening that source consumes zero Gemini tokens. Quran text remains unchanged; original reference irregularities are disclosed and the reference is editable. Run node scripts/test-sana.mjs for budget, concurrency, token ceiling, single-key exhaustion, and zero-token verse-reference tests.

This is a selected library, not all of Hisn al-Muslim; independent scholarly review is pending. Modern commentary/translations are not copied. Texts and references are served from a closed library; Gemini only selects an existing entry or category. No generated scripture, hadith, citations or fatwas are displayed. The same catalog is seeded into D1 (seeds/adhkar-v1.sql) and packaged locally for offline use. The released app uses the versioned source bundle, not arbitrary DB edits. Withdrawal requires updating the source status and redeploying/re-downloading; old offline copies are not silently revoked. ## Cloudflare encrypted synchronization

Authentication stays on the existing username/password service. No Google, Supabase, or Clerk runtime integration is enabled. Cloudflare D1 owns users, sessions, encrypted vaults, and the three most recent previous revisions. `drizzle/0002_sync.sql` adds `vaults.updated_at`, the `vault_history` table, and an atomic history trigger; it was applied with Wrangler remote execute. Do not reapply this non-idempotent migration. Existing vault ciphertext remains compatible.

Each browser account uses a separate local data key. Guest data remains separate and can be copied explicitly into an empty signed-in account. After signing in, open Account → encrypted synchronization, enter a separate vault passphrase (16+ characters), compare the device/cloud summaries, and choose the starting copy. The passphrase is never sent to Cloudflare or persisted. PBKDF2-SHA256 (250,000 iterations) derives an AES-256-GCM key kept only in memory. Uploads reuse the account vault salt and generate a fresh 96-bit IV. Auto-sync is debounced, serialized, retries temporary network failures, and polls for remote updates every 30 seconds while the page is visible. It runs only while the vault is unlocked and the page is open. Logout/reload locks it.

All vault reads/writes/history queries derive ownership from the authenticated session. A single SQL compare-and-swap update prevents stale writes; HTTP 409 pauses synchronization for explicit review. Before a cloud restore, the current device snapshot is retained locally and can be exported. The last three previous cloud revisions can be decrypted and exported without changing current data. Neither the server nor the support assistant can recover a forgotten vault passphrase. The 200 KB encrypted-payload limit remains enforced. Run `node scripts/test-sync.mjs` to verify authenticated ownership, encryption integrity, incorrect passphrases, concurrent write conflicts, history retention, and two-device synchronization.
